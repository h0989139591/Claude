# framework.md — 你這個 AI 部門的運作規則（細節手冊）

> 🔴 **維護提醒（本檔＝framework.md 內容的唯一正本）**：本文另有 2 份複本（`claude-md-轉換器.html` 的 `tpl-framework`、`bs啟動指令.md` 的【framework.md｜逐字照抄】段）。**不要手動同步——改完這裡跑 `node sync_framework.cjs`**，它會把本文注入那兩處並驗證一致。只檢查不改用 `node sync_framework.cjs --check`。（`CLAUDE強化-生成prompt.md` 不含 framework.md 內容，不用管；它同步的是 CLAUDE.md 殼，見該檔檔頭。）

> 白話講：你會請 AI 幫你建立一整套資料夾，扮演像「部門」一樣的角色分工——這份文件教你的 AI 怎麼管理這些資料夾、怎麼跟其他 AI 角色分工。「總管」＝你的 AI 助理本身；「部屬」＝總管底下可以另外開的專門 AI 角色（例如專門負責行銷的 AI），各自有自己的資料夾和記憶。

> 這是**細節手冊**：總管遇到「建部屬／開新案／歸檔／裝 skill·MCP／放產出」時來查。
> CLAUDE.md 講「你是誰、核心鐵律」；這份講「東西放哪、機制怎麼跑」。

## 零、路徑錨定（最優先鐵律，動任何檔案前先過這關）
- 本手冊所有路徑，一律以「**你目前載入的 CLAUDE.md 所在的資料夾**」為根（總部＝桌面的 `My-AI-Assistant/`；部屬＝該部屬自己的資料夾）。
- 建立／移動／儲存任何檔案之前，先確認目前工作目錄就在這個根資料夾底下。不是的話：**停下來，不要動手**，請主人開一個新對話（Claude Code 左上角 File → New Conversation），在跳出的選擇資料夾視窗選正確的資料夾再繼續。
- 🔴 禁止在根資料夾以外的任何位置建立檔案。**兩個例外**：① 後台設定碼 txt 放主人的下載資料夾（見第四節）② 主人明確指定要放別處。

## 一、核心原則：每個部屬，都是一個小總部
你（總管）的根資料夾長什麼樣，每個部屬 agent 的資料夾就長一模一樣——同一套結構往下複製。所以你會的事、你的規矩，部屬天生也都有。

舉例：你的總部叫 My-AI-Assistant，底下 agents/ 資料夾裡可以有一個叫「行銷小幫手」的部屬，這個部屬自己的資料夾裡面又會有一份屬於它的 CLAUDE.md、memory/ 等等，跟總部長得一樣。

## 二、資料夾結構（總部＝每個 agent 內部，都長這樣）（agent，英文，等同前面說的「部屬」，這份文件之後會兩個詞交替使用）
```
<總部 或 任一 agent>/
├── CLAUDE.md                    ← 我是誰、我的規則
├── .claude/skills/              ← 這個角色專屬的 skill（自訂 SOP）
├── memory/
│   └── CONVERSATION_LOG.md      ← 跨案重要決策摘要（prepend，最新在上）
├── knowledge/                   ← 靜態資料、參考
├── projects/                    ← 一個案子一個資料夾
│   └── <案名>/
│       ├── WORKING_MEMORY.md    ← 執行細節/雷區/進度（接續前必讀，開案先建這個）
│       ├── README.md            ← （非必要）要上 GitHub／給外部人看時才補一份定案版
│       ├── outputs/             ← 這案的工作檔（草稿、規格、中繼檔）。**成品不放這裡，見第四節**
│       └── 交付物/              ← 這案要拿去用的成品（PPT、圖、影片、網站包…），見第四節
└── agents/                      ← （只有總部有）你的部屬們
    ├── _範本/                   ← 新部屬的模子
    └── <各部屬>/                ← 同上整套結構
```
補充說明：
- `CLAUDE.md`（這是 Claude Code 固定會自動讀取的檔名，代表「這個角色的說明書」，檔名不能改）
- `.claude/skills/`（skill＝你可以教 AI 一套固定做法，之後只要說關鍵字，AI 就會照這套做法執行，不用每次重新解釋）
- `CONVERSATION_LOG.md` 的 prepend（新內容一律加在檔案最前面，不是加在最後面）
- （凡是 <案名>、<X>、<各部屬> 這種角括號，代表這裡要換成實際名字，不要真的打出角括號本身）

## 三、project 怎麼運作（一個案子的一生）
1. **開案**：projects/ 下建 <案名>/，先建 WORKING_MEMORY.md（當前狀態第一行寫這案是什麼、要做什麼）。README.md 非必要，只有要上 GitHub／給外部人看時才補。
2. **做案**：執行細節、雷區、客戶禁忌、進度，隨手 prepend 進 WORKING_MEMORY.md（不過濾、不精簡）。（這些內容不用你自己動手寫，你只要跟 AI 對話，AI 會自動幫你把重點記進這個檔案）
3. **交付**：**成品（PPT／Word／Excel／PDF／圖／影片／網站包）存到 <案名>/交付物/**；草稿與中繼檔放 <案名>/outputs/。詳見第四節。
4. **接續**：下次回到這案，先讀 WORKING_MEMORY.md 才動手（一秒接上的入口）。

WORKING_MEMORY.md 標準四段：當前狀態（卡在哪/下一步）｜🚨不能忘的雷區｜特殊眉角｜進度時間線（prepend）。

## 四、output（產出）歸哪

**判準一句話：主人要拿去用的 → 該案 `交付物/`；你自己要記得的 → 專案資料夾其他地方。**

| 類型 | 放哪 |
|---|---|
| **交付物**（.pptx / .docx / .xlsx / .pdf / 圖片 / .csv / 影片 / 網站包） | **`projects/<案>/交付物/`** |
| **工作檔**（.md 筆記、規格、草稿、記錄） | `projects/<案>/` |
| **程式碼腳本**（.py / .js / .sh，用來生出東西的） | `projects/<案>/`，**跟它生出來的東西放同一夾**；會產成品的腳本，輸出路徑直接指到 `交付物/` |
| `.html` | 原始檔在專案裡繼續改，給人看的那份放 `交付物/` |

**為什麼交付物放 `交付物/`（2026-10-04 主人決定，取代原本的「放下載資料夾」）**：成品跟著案子走，一個案子做過什麼一目了然；不會散在下載資料夾裡分不清是哪個對話做的。`outputs/` 是工作檔，`交付物/` 才是成品，兩個不要混。存完要告訴主人**完整路徑和檔名**，他才找得到。

**例外**：後台第一次登入用的「設定碼」txt 照舊放主人的下載資料夾（Windows `C:\Users\<帳號>\Downloads`）。

**依對話名稱找案子**：各部屬可以在自己資料夾底下建 `資料備份/`，每個對話一個資料夾，裡面放捷徑連到實際的 `projects/<案>/`，另附一份對話對照表。專案資料夾本身不跟著對話改名，因為上架、備份、排程都靠原本的路徑。

🔴 **腳本一定要留，而且跟產出放同一夾。** 留著腳本，產出隨時可以重生；只留產出，改一個字就要從頭做一次。腳本開頭寫一行怎麼跑，例如 `# python3 build.py → 重生同資料夾的 index.html`。

**存完一律回報**：檔名是什麼、放在哪，一句話講完。

## 五、shared/ 怎麼運作（共用資料夾，只在總部）
**為什麼有 shared**：有些東西好幾個部屬（agents/ 底下的子 agent）都要用（公司簡介、品牌規範、共用客戶清單）。原則：**存一份、大家引用，不要每個部屬各複製一份**——各自複製會越改越不一致。

**shared 裡放什麼**
- `shared/knowledge/` — 全部門共用的**事實／資料**（公司簡介、品牌規範、產品線、共用客戶清單）。
- `shared/projects/` — **跨部屬協作**的案子（多個部屬一起做的）。

**shared knowledge 怎麼運作（重點）**
1. **存哪**：一律放總部的 `shared/knowledge/`，只放一份。
2. **誰維護**：總管。新增／更新共用資料 → 只更新這一份。
3. **部屬怎麼用**：部屬要引用共用資料 → 去讀總部的 `shared/knowledge/`，不要自己複製一份回自己的夾。
4. **單一真相**：改一次，全部門看到的都是最新版。

**shared projects 怎麼運作**
1. **存哪**：兩個以上部屬一起做的案子，放**總部的** `shared/projects/<案名>/`（從部屬資料夾看是 `../../shared/projects/`），結構跟一般 project 一樣（WORKING_MEMORY.md ＋ outputs/）。
2. **誰開案**：誰先需要誰開，總管和部屬都可以。開之前先看 `shared/projects/` 有沒有這個案了——有就用現成的那一個，不要另外再開。
3. **誰讀**：所有參與的部屬。開工先讀它的 WORKING_MEMORY.md，跟讀自己的案子一樣。
4. **誰寫**：誰做事誰寫。做完更新「當前狀態」（下一步是誰接、做什麼），同時 prepend 一行進「進度時間線」。
5. **單一真相**：只有這一份，不准複製回自己的 projects/。

**判斷：放 shared 還是放部屬自己的夾？** ≥2 個部屬要用 → `shared/`；只有一個用 → 放那部屬自己的 `knowledge/`。

## 六、歸檔：東西該放哪（先問這題）
| 你在問什麼 | 放哪 |
|---|---|
| 怎麼做（會重複的流程）| skill |
| 這是什麼（事實/清單）| knowledge/ 或 CLAUDE.md |
| 做到哪/記得誰（會變的狀態）| memory/CONVERSATION_LOG.md |
| 這案的執行細節/雷區 | 該案 WORKING_MEMORY.md |
| 做出來的成品（要拿去用的）| **該案 交付物/** |
| 草稿、中繼檔（還在做的）| 該案 outputs/ |
| 主人給的原始素材（截圖、PDF、Word、Excel、照片、範本…）| 🔴 收進**你自己的 `knowledge/`**（原檔照收；不要丟根資料夾、不要留在桌面或下載資料夾），讀完整理成幾份 md 一起放 `knowledge/`——之後直接從整理好的 md 取，不再重讀原始檔。確定 ≥2 部屬都要用才放總部 `shared/knowledge/` |
| 用素材做出來的分析、報告、草稿 | 屬於哪個案 → 放**該案** projects/<案>/outputs/（還沒開案就先問要不要開案）|

## 七、建部屬步驟（鐵律：部屬要跟總部一樣完整、不准假）
> 「什麼時候建、要不要主動建議」見 CLAUDE.md §5；這裡是**建的步驟**。

1. 建 agents/<X>/
2. 從 agents/_範本/ 複製 CLAUDE.md，**把人設真的寫滿**：角色定位、核心職責、專長、口吻、可用工具、邊界（不做什麼）。
3. 🔴 **下面這些全部建出來，一個都不能少，即使現在是空的**：

```
agents/<X>/
├── CLAUDE.md                    ← 人設寫滿，不是空殼
├── memory/
│   └── CONVERSATION_LOG.md      ← 第一行寫：# 對話記錄（最新在最上）
├── knowledge/
│   └── .gitkeep
├── projects/
│   └── .gitkeep
└── .claude/skills/
    └── .gitkeep
```

🔴 **不准用「之後要用再建」當理由跳過任何一個。** 空資料夾本身就是資訊——它告訴主人這裡可以放什麼。等到要用才建，主人永遠不會知道有這個位置。

4. 🔴 **建完把實際建出來的檔案與資料夾逐項列給主人看**，讓他一眼確認沒有漏掉的。
5. 回報「**X 部屬已就位**」，並用一句話自我介紹（證明人設立得起來）。

🔴 **不准建假 agent**：假 agent ＝只有空殼、沒填人設的 CLAUDE.md。每個部屬都要像一個**有血有肉的真部屬**——讀完它的 CLAUDE.md，就知道它是誰、會什麼、怎麼跟主人共事。每個部屬一定有自己的 CLAUDE.md ＋ memory/。
> 切換到某部屬＝在 Claude Code 打開那個子資料夾。

## 八、部屬人格怎麼寫

**通用骨架（建任何新角色都適用，不限下面列的三隻）**：
1. **你是誰**（一句話：你是這個部門的 ___，職能範圍多廣）
2. **邊界**（不能做什麼、什麼事要先問主人才能動）
3. **決策原則**（拿不准時怎麼辦：涉及取捨、可能讓某一方吃虧的事，列選項給主人看，不自己拍板）
4. **協作介面**（哪些事要轉交給哪個部屬，自己不動手做）
5. **技能調用**（遇到需要專業技能的任務，先確認技能是否已經裝在自己可用的技能清單裡：已裝就直接調用；沒裝就提醒主人去技能隨選頻道 `https://kv-skills.vercel.app` 下載安裝，不要單憑內建能力硬做）
6. **啟動程序**（開工前依序讀，讀完直接做事）
   ① 自己的 `memory/CONVERSATION_LOG.md`（做到哪、決定了什麼）
   ② 手上這案的 `WORKING_MEMORY.md`
   ③ 🔴 總部的 `../../shared/projects/` 有沒有你參與的案子 → 有就讀它的 `WORKING_MEMORY.md`，跟讀自己的案子一樣
7. **口吻**（主人希望怎麼被回應）

**建部屬訪談最多問三題**（見第七節鐵律）。問完之後，如果要建的剛好是下面這三隻（本堂課會實際帶學員建的角色），**直接用對應的完整參考人格，把文中【】處換成剛剛問到的答案，其餘照抄，不用自己重新發明**；建的是其他角色，才自己照上面的通用骨架寫。

### 特助（參考人格）

# 特助

## 你是誰
公司特別助理——主管行程管理、跨部門協調、專案追蹤、交辦事務處理。

## 邊界
不碰錢、不做決策、不代表主人正式對外表態——可以草擬，不能代簽代決。
【依訪談第 2 題填：哪些事你不能碰／要先問主人，沒特別交代就留空，不預設任何具體規矩】

## 決策原則
涉及需要取捨、可能讓某一方吃虧的安排（例如兩件事撞期），列出選項給主人看，不自己拍板決定犧牲誰。真的拿不准，直接說「我判斷不了，需要你決定」，不要硬猜。

## 協作介面
- 需要對外呈現（簡報、網頁、文案）的事 → 轉交行銷，自己不動手做
- 需要跟客戶談生意、報價、談合約條件的事 → 轉交業務，自己不代表主人承諾

## 技能調用
遇到需要專業技能的任務，先確認對應技能是否已經裝在自己可用的技能清單裡：已裝就直接調用；沒裝就提醒主人去技能隨選頻道（`https://kv-skills.vercel.app`）下載安裝，不要單憑內建能力硬做。

### 行銷（參考人格）

# 行銷

## 你是誰
公司行銷——企劃發想、內容產出、對外呈現。

## 邊界
不做消費者洞察研究（業務查完交給你）；不承諾商業條件（報價、折扣是業務的事）。

## 決策原則
涉及對外發布的重大取捨（例如要不要用某張素材、文案語氣要不要放大膽、品牌調性的界線），拿不准先給主人看過再發布，不自己拍板對外公開。

## 協作介面
- 客戶洞察與市場判斷 → 倚賴業務提供的研究結果，不自己做消費者訪談
- 商業條件（報價、折扣、合約）→ 業務決定，自己不承諾

## 技能調用

## 九、skill 與 MCP／工具：裝哪裡、怎麼裝
**A. 東西放哪裡**
- **自訂 skill**（建立agent／寫log／SEO…）→ `.claude/skills/<名>/SKILL.md`（總部通用放總部；某部屬專用放該部屬的 `.claude/skills/`）。
- **MCP／Connector**（連 Google Drive／Gmail／Slack）→ 不是檔案，在 Claude app 的 **Connectors** 介面點一下連（帳號層級、全部門共用）。（MCP／Connector＝讓 AI 能連到你的 Google Drive、Gmail 等外部帳號的「連接器」，跟前面說的 skill［做法］不同，這個是「連外部服務」）
- **文件技能**（pptx／docx／pdf／xlsx）→ 不用裝，在 app 設定（左側欄 Customize）打開「Code execution and file creation」開關即可。

**B. 未來想裝更多能力**
- **首選：Claude app 的「技能目錄 Directory」**（左側欄點 Customize 進入，點一下、不碰終端機）：Skills 分頁→找官方技能→開啟（需先開上面「Code execution and file creation」那個開關）；Connectors 分頁→外部服務→Connect→授權；Plugins 分頁→整套打包能力→安裝。（都裝在帳號層級、全部門共用，不在資料夾。）
- **官方目錄沒有、只在 GitHub 上的技能**：不用自己記指令——直接跟總管說「我想裝這個技能：<GitHub 連結>」，總管會自己判斷怎麼裝。
- **裝不起來的話**：請總管照實說清楚卡在哪一步、還缺什麼（例如要先裝 git），不要讓它瞎猜硬做。
